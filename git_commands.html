Read this first

Git tracks snapshots in three places.

Git does not save every file change the moment you edit it. Work moves through a simple pipeline: edit files, choose what belongs in the next snapshot, then commit that snapshot into local history.

01

Foundations

Initialization

Turn an ordinary folder into a Git repository, create a project folder and repository in one step, or remove the repository layer entirely.

Git Safe

Create a repository in the current folder

terminal bash 
$ git init
Initialized empty Git repository in ~/projects/website/.git/

Creates the hidden .git directory in the current folder. That directory holds the object database, branch references, configuration, and the rest of the repository metadata. Existing files are left alone, but none of them are tracked or committed yet. The initial branch name depends on your Git version and init.defaultBranch setting—commonly main or master.

i
Initialization is not a commit.

Until you stage and commit something, the repository has no history and git log has nothing to show.

Git Safe

Create a named project folder and repository

terminal bash 
$ git init "project name"
Initialized empty Git repository in ~/projects/project name/.git/

Creates a directory named project name if it does not exist, then initializes a repository inside it. If the directory already exists, Git initializes that existing folder without deleting its contents. This is a quick way to start a project without creating the folder separately.

Arguments

"project name"
The target directory. Keep it in quotes when the path contains spaces. Git creates the directory if needed and places .git inside it.
↳
Already have a folder?

Pass its name instead, or cd into it and run plain git init.

Shell Destructive

Remove Git from a project

terminal bash 
$ rm -rf .git

Deletes the entire .git directory. Your working files stay on disk, but every local commit, branch, tag, remote, stash, and repository setting disappears. The folder is no longer a Git repository. This is a shell command, not a Git command, and it is not something Git can undo.

Flags & arguments

-r
Recursive. Required to delete a directory and everything inside it. Without it, rm refuses to remove a directory.
-f
Force. Suppresses confirmation prompts and missing-file errors. Together, -rf deletes recursively without asking.
.git
The repository database. The hidden folder at the project root. Remove it only if you are intentionally converting the folder back into a plain directory.
!
There is no local undo.

If a remote contains the history, you can clone it again. Local-only commits and stashes have no copy and will be gone. Use Git Bash for this syntax on Windows.

02

Identity & scope

Configuration

Git writes your name and email into every commit, so set them before you start. Global settings apply to all repositories; local settings override them for one project.

Git Config

Set your global name

terminal bash 
$ git config --global user.name "your name"

Stores the author name Git will attach to commits created on this computer. The value belongs to the current operating-system user, not to Git itself, and applies to every repository that has no more specific local override. It can be your real name or a consistent handle; Git does not validate it.

Flags & arguments

--global
User-wide scope. Writes to ~/.gitconfig (or the equivalent for your account) and affects every repository for this OS user.
user.name
The name key. The author name recorded in new commits. It is not your Git hosting username or password.
"your name"
The value. Replace it with your actual name. Quotes keep a multi-word value together as one argument.
↳
Set this before your first commit.

Git will use this identity for every new commit unless a repository-local value takes priority.

Git Config

Set your global email

terminal bash 
$ git config --global user.email "your@email.com"

Sets the email address attached to your commits. Hosting platforms such as GitHub, GitLab, and Bitbucket use this address to connect commits to an account. Use the email associated with those accounts, or the no-reply address they provide if you prefer not to publish a personal email.

Flags & arguments

--global
User-wide scope. Applies to all repositories for this account unless a local value overrides it.
user.email
The email key. The address Git records as the commit author's email.
"your@email.com"
The value. Replace it with the address you want associated with your commits.
Git Config

Set a repository-only name

terminal bash 
$ git config --local user.name "your name"

Writes the name into the current repository's .git/config file. That local value takes precedence over the global value for commits made in this repository. It is useful for separating work and personal identities without changing every project on the machine. You must run it inside a repository.

Flags & arguments

--local
One-repository scope. Writes to .git/config inside the current repository and overrides global settings there.
user.name
The name key. The author name for commits in this repository.
"your name"
The value. Quote multi-word names. It is stored only for this project.
i
Local wins over global.

If both exist, this repository's local name is used. Other repositories keep using your global identity.

Git Config

Set a repository-only email

terminal bash 
$ git config --local user.email "your@email.com"

Sets a commit email for this repository only, stored in .git/config. Use it when a project must be associated with a different address—for example, a work email for an employer's repository. It overrides the global email in this repository without touching the rest of your projects.

Flags & arguments

--local
One-repository scope. Targets the current repository's config file and takes precedence over the global email.
user.email
The email key. The address recorded on commits made in this repository.
"your@email.com"
The value. Replace it with the address this repository should use.
Git Read only

Read your global name

terminal bash 
$ git config --global user.name
ahmed ghnnam

When git config receives a key but no value, it reads that key instead of writing it. With --global, it reads only the global file. It does not fall back to a repository-local value. If the key is unset, Git prints nothing and exits with a non-zero status.

Flags & arguments

--global
Reads the global scope only. A local value in the current repository is ignored.
user.name
The key to read. Omitting the value argument turns the command into a getter.
Git Read only

Read your global email

terminal bash 
$ git config --global user.email
ghnnam@example.com

Prints the globally configured commit email. This is a safe inspection command: it changes no files. It is also useful for checking which address will be attached to new commits before you publish them. A blank result means no global email is set.

Flags & arguments

--global
Reads the global scope only. Use it to verify the fallback identity for every repository.
user.email
The key to read. No value follows, so Git prints the stored value.
Git Read only

Read this repository's name

terminal bash 
$ git config --local user.name
khabib

Reads the name from the current repository's config file only. This is the value that will override your global name here. If the repository has no local name, the command returns nothing—even when a global value exists—so it is a precise scope check rather than an effective-identity check.

Flags & arguments

--local
Reads this repository only. It looks at .git/config and does not fall back to your global identity.
user.name
The key to read. Leave off a value so Git reports the stored name instead of setting it.
Git Read only

Read this repository's email

terminal bash 
$ git config --local user.email
khabib@work.example

Prints the commit email stored for this repository alone. Use it to confirm that a project-specific identity is configured, or to check which address will appear in the next commit. Like the other local read commands, it does not show global fallbacks.

Flags & arguments

--local
Reads this repository only. The global value is not displayed, even when no local value exists.
user.email
The key to read. With no value supplied, Git returns the configured address.
Git Read only

List all active configuration

terminal bash 
$ git config --list
user.name=ahmed ghnnam
user.email=ghnnam@example.com
init.defaultbranch=main
alias.st=status
alias.cm=commit -m

Prints the configuration Git can see from the system, global, and local scopes for the current context. Because the same key may be defined more than once, it can appear multiple times; the most specific applicable value wins. Use it to verify identities, aliases, and repository behavior without opening any config files.

Flags & arguments

--list
List mode. Prints every configuration entry Git can resolve instead of expecting a key and value. No scope flag means all applicable scopes are included.
Git Config

Remove your global name

terminal bash 
$ git config --global --unset user.name

Deletes the user.name entry from your global configuration. Local repository identities are untouched. Afterward, Git may use a system-level value or auto-detect an identity, and it may warn you to configure one before committing. If the key does not exist, Git returns an error.

Flags & arguments

--global
Targets the global file. The current repository's local identity, if any, remains in place.
--unset
Remove a key. Deletes the matching setting instead of assigning a new value. If the key is missing, the command fails.
user.name
The key to remove. Only this name entry is deleted.
↳
Check before removing.

Run git config --global user.name first so you know what value you are about to clear.

Git Config

Remove your global email

terminal bash 
$ git config --global --unset user.email

Removes the global commit email while leaving repository-local emails intact. New commits will need an identity from another configuration scope or from Git's auto-detection, so expect a warning if nothing replaces it. Use this when moving identities or cleaning up a shared machine.

Flags & arguments

--global
Targets the global file. Project-specific emails are not affected.
--unset
Remove a key. Deletes the stored setting rather than overwriting it. Missing keys produce an error.
user.email
The key to remove. Only the email entry is cleared.
03

Shortcuts

Aliasing

An alias is a short name for a longer Git command. Aliases live in your Git configuration, so they are just as portable—and as easy to remove—as any other setting.

Git Alias

Create a custom alias

terminal bash 
$ git config --global alias.<name> "<git command>"

Creates an entry in the [alias] section of your global configuration. Afterward, git <name> expands to the command stored as its value. An alias is not a copy of the command and does not change Git itself—it is simply a shortcut that Git resolves before running the real command.

The name must be a single token such as st, br, or lg; spaces are not allowed. The command value may contain spaces and flags, so wrap the whole value in quotes. The phrase "alias name" in the raw list is a placeholder, not a literal legal alias.

Flags & arguments

--global
Every repository. Saves the alias in your user-wide config. Use --local instead to limit it to the current project.
alias.<name>
The alias key. Replace <name> with a one-word shortcut. Git treats it as a command name after git.
"<git command>"
The command string. The Git subcommand and any flags it should run. Quotes preserve the spaces as one value.
!
Spaces are not part of a valid alias name.

Write alias.st, not alias."my status". Git rejects an alias key containing a space.

Git Alias

Shorten status to st

terminal bash 
$ git config --global alias.st status

Makes git st an exact shorthand for git status. The value is a single word, so no surrounding quotes are needed. This is one of the most common Git aliases because status is a command you will run constantly.

Flags & arguments

--global
Available everywhere. The shortcut is stored for your user account rather than this one repository.
alias.st
The shortcut. st is the key; the resulting command is git st.
status
The command value. The one-word Git command that the alias expands to.
Git Alias

Shorten branch to br

terminal bash 
$ git config --global alias.br branch

Maps git br to git branch. The alias passes through exactly as written, so it can also replace the subcommand in longer commands you type later. It does not take arguments or add flags on its own.

Flags & arguments

--global
Available everywhere. Stores the shortcut in your user-wide configuration.
alias.br
The shortcut. br becomes a new subcommand alias.
branch
The command value. The Git command that git br expands to.
Git Alias

Bundle a flag into a commit alias

terminal bash 
$ git config --global alias.cm "commit -m"
$ git cm "Add branching reference"
[main 9b1d4c0] Add branching reference

Stores commit -m as the value of the cm alias. The quotes keep the space between commit and -m inside one config value. Running git cm "Add branching reference" is then equivalent to running git commit -m "Add branching reference".

Flags & arguments

--global
Available everywhere. The alias is saved for every repository under your user account.
"commit -m"
The full alias value. Quotes preserve the space so Git sees one command string, not a command plus an unrelated argument.
-m
Message inline. Short for --message. It supplies the commit message on the command line and skips the editor, so the message must follow immediately.
↳
The alias expects a message.

Use git cm "Describe the change". Running git cm alone leaves -m without its message and Git will reject it.

04

Direct access

Editing configuration

Git configuration is plain text. Open it directly when you need to change several settings at once or review the structure behind the individual config commands.

Git Editor

Open the global config in your editor

terminal bash 
$ git config --global --edit

Opens your global Git configuration file in the editor Git is configured to use. Saving the file writes the changes; closing without saving leaves the configuration untouched. The file is grouped into sections such as [user] and [alias], with entries written as key = value.

Git chooses the editor from core.editor, then the GIT_EDITOR environment variable, then your usual editor variables, and finally a system default such as Vi. If the file is malformed, Git may fail to read the affected configuration until the syntax is fixed.

Once the file is open, you can add whole sections by hand. The example below changes the colors of git status and branch labels, then declares the st and cm aliases. Save the file and close the editor to apply all of it at once.

Example saved file ~/.gitconfig

~/.gitconfig ini 
[color "status"]
    added = green
    changed = red bold
    untracked = cyan bold

[color "branch"]
    local = green
    remote = yellow
    current = bold green

[alias]
    st = status
    cm = commit -m

Section names in quotes, such as [color "status"], are subsection headers. Each entry sets a key to a value: the status entries map to color.status.added, color.status.changed, and color.status.untracked; the branch entries map to color.branch.local, color.branch.remote, and color.branch.current. Color values accept a base color plus optional attributes such as bold, so red bold renders changed files in bold red. The alias entries are equivalent to running git config --global alias.st status and git config --global alias.cm "commit -m". On Windows, the global file is usually C:\Users\<you>\.gitconfig; run git config --global --list --show-origin to print its exact location.

Flags & arguments

--global
Selects the global file. With --edit, it opens the user-wide config rather than the current repository's config.
--edit
Open in an editor. Starts your configured editor instead of reading or writing a single key from the command line. Git applies the changes when you save.
i
Prefer one-key commands for small changes.

Direct editing is efficient for several settings, but a mistyped section or value can make Git configuration unreadable. Keep a backup if you are experimenting.

05

Outside Git

File operations

These are shell commands, not Git commands. They create and remove files on disk; Git only notices the result the next time you inspect its status. The exact syntax here targets macOS, Linux, or Git Bash.

Shell Safe

Create an empty file

terminal bash 
$ touch "file name"

Creates an empty file if it does not exist, or updates its modification timestamp if it does. The new file is not tracked and is not staged. Git will list it as untracked until you add it. Use quotes when the filename contains spaces.

Arguments

"file name"
The path to create or touch. Quotes keep a name with spaces together. This command has no Git flags and makes no changes to the index.
i
Shell portability.

touch is native to Unix-like terminals and Git Bash. Windows PowerShell uses a different command, so use Git Bash if you want this exact syntax.

Shell Destructive

Delete a file or folder

terminal bash 
$ rm -rf "file name"

Removes the named file or directory from disk. If Git was tracking it, the file disappears from the working tree and appears as a deletion in git status; stage that deletion and commit it to record the removal. If the file was untracked, there is no Git record of its contents at all.

Flags & arguments

-r
Recursive. Delete directories and their contents. Without it, rm will not remove a directory.
-f
Force. Suppress prompts and ignore missing paths. Combined as -rf, it removes recursively without confirmation.
"file name"
The target path. A file or directory. Quote paths with spaces, and check that you are in the intended directory.
!
This is not git rm.

The shell does the deleting; Git only records the aftermath. Uncommitted or untracked content is gone permanently. A tracked file can be restored only if its content exists in a commit.

Shell Destructive

Delete everything in the current folder

terminal bash 
$ rm -rf *

The shell expands * to every non-hidden file and directory in the current directory, then asks rm to delete them recursively and forcefully. Hidden entries—including .git, .gitignore, and .env—are normally skipped, so the repository metadata may survive while all visible working files disappear.

Flags & arguments

*
Shell wildcard. Expands to visible entries in the current directory only. It is expanded before Git or rm ever sees it.
-r
Recursive. Removes directories and everything nested inside them.
-f
Force. Deletes without asking for confirmation. There is no dry-run in this command and no recycle bin.
!
Do not run this from a home or system directory.

Even with .git intact, restoring hundreds of files is painful; untracked work is irrecoverable. If you only need to remove ignored build output, use a targeted path instead.

06

Read the state

Status & history

Two read-only commands answer most questions. git status compares your working tree and index with the last commit, while git log walks the commits themselves. Run both before you branch, merge, clean, or delete anything.

Git Read only

See what changed

terminal bash 
$ git status
On branch main
Your branch is up to date with 'origin/main'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   index.html

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
        modified:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        notes.md

git status is a report, not a mutation. It compares three snapshots: the last commit (HEAD), the index—what would go into the next commit—and the working tree, meaning the files on disk. It tells you which changes are staged, which are unstaged, and which files Git has never tracked. Nothing is added, removed, or committed by reading this output.

Untracked files are invisible to commits until you stage them. A file that appears under both “Changes to be committed” and “Changes not staged for commit” has staged content plus newer edits that are not yet in the index.

i
Short form.

git status --short prints one compact line per file; add --branch to include the branch name and ahead/behind counts. Neither form changes the repository.

Git Read only

Inspect commit history verbosely

terminal bash 
$ git log -v
commit 8f3c1a2d9e4b7a6c5f0e1d2c3b4a5968778695a4
Author: Ada Lovelace <ada@example.com>
Date:   Thu Nov 12 14:32:08 2026 +0200

    Add setup instructions

commit 4b7d2e19c0a8f3e5d6b7c8a9f0e1d2c3b4a59687
Author: Ada Lovelace <ada@example.com>
Date:   Wed Nov 11 09:18:44 2026 +0200

    Create project skeleton

git log lists commits reachable from HEAD in reverse chronological order, showing the full hash, author, date, and message for each. -v requests the verbose commit header. That header is already shown by default in current Git, so the output often looks identical to plain git log. It does not add a diff.

This is a common surprise: -v is not a patch flag. To see which files changed, add --stat; to read the actual changes, add -p.

Flags & arguments

-v
Verbose header. Asks for the full commit header: hash, author, date, and message. Git already prints this by default, so the result can look unchanged. It does not show a diff.
--stat
Optional add-on. Lists the files changed in each commit with insertion and deletion counts. This is the quickest way to see scope without a full patch.
-p
Optional add-on. Shows the complete patch introduced by each commit. Output gets long quickly; the pager opens automatically, and q quits it.
--stat Summary of changed files and line counts.
-p Full diff for every commit in the range.
07

The staging area

Staging & restoring

The index—also called the staging area—is the exact snapshot the next commit will record. git add moves changes into it, git restore --staged moves them back out, and git clean deals with files Git has never tracked at all.

Git Safe

Stage a file for the next commit

terminal bash 
$ git add "file name"
$ git status --short
A  file name

Copies the current contents of a path into the index. The file is now staged: it will be included in the next commit, but nothing has been committed yet. Staging does not freeze future edits. If you change the file again, those newer edits stay unstaged until you run git add once more.

Adding an untracked file makes Git start tracking it. Quotation marks are shell syntax that keep a filename containing spaces together—they are not part of the filename itself.

Flags & arguments

"file name"
The path to stage. Git calls this a pathspec; it can name a file, a directory, or a pattern. Quotes preserve spaces in the shell; they are removed before Git sees the name.
↳
Staging more than one file.

git add . stages changes below the current directory; git add -A covers the whole repository, including deletions. Both still stop short of committing.

Git Safe

Unstage a file without losing edits

terminal bash 
$ git restore --staged "file name"
$ git status --short
 M file name

Rewrites the index entry for a path using HEAD as the source, leaving the working tree alone. The edits stay on disk and move from “Changes to be committed” back to “Changes not staged for commit.” If the path was newly added and has no HEAD version, it returns to being untracked.

The --staged flag is the safety switch. Without it, git restore would overwrite the working-tree file from the index instead—discarding the very edits you may be trying to keep.

Flags & arguments

--staged
Operate on the index. Restores the staged entry from --source (HEAD by default) and leaves the working tree untouched. The older spelling is --cached.
"file name"
Required pathspec. Unlike the working-tree form, --staged needs an explicit path so Git knows which index entries to reset. Quote names that contain spaces.
i
Older Git versions.

git reset HEAD -- "file name" performs the same index-only reset. git restore --staged is the clearer modern form, available since Git 2.23.

Git Preview

Preview untracked files that would be removed

terminal bash 
$ git clean -n
Would remove draft.md
Would remove notes.tmp

git clean removes untracked files—files Git has never been asked to track. -n is the dry run: it prints the paths it would remove and exits without touching disk. Always run this before the forceful version. Ignored files are excluded by default, and untracked directories are skipped unless you add -d.

Flags & arguments

-n
Dry run. Prints one Would remove … line per path and deletes nothing. It is the long form of --dry-run and needs no confirmation.
-d
Optional: include directories. Without it, clean does not descend into untracked directories, so their contents are not listed or removed.
-x
Optional and dangerous: include ignored files. Adds build output, dependency caches, and local .env files to the preview. Try git clean -nx before using it for real.
↳
Preview, then repeat with force.

Read the list, then run the same command with -f—and with -d if directories appeared because you asked for them. The preview itself is completely safe.

Git Destructive

Delete untracked files permanently

terminal bash 
$ git clean -f
Removing draft.md
Removing notes.tmp

-f turns the preview into a permanent deletion. Git removes untracked files and stops; tracked files and staged changes are not touched. There is no commit to revert and no recycle bin. Ignored files are left alone unless you add -x, and directories require -d.

Git requires -f because clean.requireForce defaults to true. A bare git clean prints a warning and exits instead of deleting anything.

Flags & arguments

-f
Force the deletion. Also written --force. Required by default; it confirms that you really want to remove untracked data.
-d
Optional: recurse into untracked directories. Without it, only untracked files in the current tree are removed and directories are left in place.
-x
Optional and extra dangerous: include ignored files. Deletes build artifacts, dependency caches, and local secrets alongside ordinary untracked files.
!
No undo.

git clean -f creates no commit, stash, or backup. Run git clean -n first, and add -d or -x only when you intend to include directories or ignored files.

08

Record a snapshot

Committing

A commit records the staged snapshot, a message, and a pointer to its parent. Plain git commit opens an editor for the message; -m supplies it inline. Only staged content goes in, so review git status first.

Git Safe

Commit the staged snapshot

editor flow bash 
$ git commit
# Your editor opens with a commit-message template.
# Write the message, save, and close the editor.
inline message bash 
$ git commit -m "Add setup instructions"
[main 8f3c1a2] Add setup instructions
 1 file changed, 12 insertions(+)

A commit is a snapshot of the index, not of the working tree. Only staged changes are recorded; unstaged edits remain on disk. Plain git commit opens the editor configured in core.editor so you can write the message. git commit -m "…" supplies the message on the command line and skips the editor entirely.

Each commit also records a parent pointer, author, and timestamp. Write the message to explain why the change was made; the diff already shows what changed. If the index is empty, Git refuses with “nothing to commit.”

Flags & arguments

-m "message"
Inline commit message. Uses the quoted text as the message and skips the editor. Repeat -m to add further paragraphs without opening a file.
-a
Optional: stage tracked files first. Before committing, stages modifications and deletions of files Git already tracks. Untracked files are not included, so they still need git add.
i
Nothing staged?

Stage a file with git add first. git commit -am "…" is a shortcut for tracked modifications, but it never picks up brand-new untracked files.

Git Destructive

Restore a file from an older commit

terminal bash 
$ git restore --source=HEAD~1 "file name"
$ git status --short
 M file name

Replaces the working-tree copy of a path with the version stored in another commit. --source=HEAD~1 names that commit; HEAD~1 means the first parent of the current commit. The index and HEAD are unchanged, so the restored content appears as an unstaged modification that you can review, stage, and commit.

Use it to recover one file from history without resetting the branch. It is not a checkout of the whole commit, and it does not move HEAD. The path argument is mandatory: git restore --source=HEAD~1 alone has nothing to restore and exits with an error.

Flags & arguments

--source=HEAD~1
The revision to read from. HEAD~1 is one commit before HEAD; a full hash, tag, or branch name works too. If omitted, the working tree is restored from the index instead.
"file name"
Required pathspec. Identifies which path to overwrite. Quote names with spaces. If the path does not exist in the source commit, the command fails instead of deleting the file.
--staged
Optional: write to the index. Restores the old content into the index instead of the working tree. The file on disk stays as it is, and the change becomes staged for the next commit.
!
Overwrites uncommitted edits.

Any unsaved changes in that path are replaced. Commit or stash them first. To inspect an old version without overwriting anything, use git show HEAD~1:"file name".

09

Parallel lines

Branching

A branch is a movable pointer to a commit; HEAD decides which pointer moves when you commit. These commands list, rename, and delete local branches. Deleting a branch removes the name, not necessarily the commits behind it.

Git Read only

List local branches

terminal bash 
$ git branch
* main
  feature/login
  fix-typos

With no arguments, git branch lists local branches. The asterisk marks the branch HEAD is attached to—the one that will receive the next commit. Listing is read-only: it does not create, switch, or delete anything.

Branch names are single tokens. Slashes are allowed for grouping, as in feature/login; spaces are not. A branch is just a pointer to one commit, so the list shows names rather than snapshots.

-a Include remote-tracking branches such as origin/main.
-v Add each branch's short commit hash and subject line.
↳
Create and switch in one step.

git branch new-branch creates a branch at HEAD but leaves you where you are. git switch -c new-branch creates it and moves you onto it.

Git Safe

Rename a branch

terminal bash 
$ git branch -m new-name
$ git branch
* new-name
  feature/login

Renames a branch without changing its commits. With one name, it renames the current branch; with two, it renames the first to the second. The reflog and branch configuration move with it, and the old name stops existing locally.

Renaming is local only. If the branch was already pushed, the remote still has the old name; push the new name and delete the old remote ref separately. The new name must be a single token, and it must not collide with an existing branch.

Flags & arguments

-m
Move/rename. Refuses to overwrite an existing branch name, which makes it the safer form. Use -m old-name new-name to rename a branch you are not on.
new-name
The new branch name. One token with no spaces; a slash is allowed for grouping, as in feature/new-name.
-M
Optional: force the rename. Overwrites an existing branch with the target name. Use it only when you deliberately intend to replace that branch.
↳
Remote still unchanged.

After renaming a pushed branch, publish the new name with git push origin -u new-name, then delete the old one with git push origin --delete old-name.

Git Safe delete

Delete a merged branch

terminal bash 
$ git branch -d feature/login
Deleted branch feature/login (was 4a1b2c3).

Deletes a local branch ref after verifying that its commits are already reachable from the current branch or its upstream. Git refuses if the branch contains work that would become unreachable. This is the safe delete.

The commits are not erased immediately. They remain in the object database and reflog until garbage collection, but no normal branch points to them. You cannot delete the branch you are on; switch away first.

Flags & arguments

-d
Delete with a merge check. Long form: --delete. If the branch is not fully merged, Git stops and suggests -D instead.
feature/login
The branch to remove. Must not be the current branch. Branch names are single tokens; this one uses a slash for grouping.
↳
What is safe to remove?

git branch --merged lists branches already contained in HEAD. Deleting a local branch does not delete origin/feature/login; the remote branch remains.

Git Destructive

Force-delete a branch

terminal bash 
$ git branch -D feature/experiment
Deleted branch feature/experiment (was 9c8d7e6).

-D is --delete --force: it removes the branch even when its commits are not merged. Those commits become unreachable from any branch. They can often be recovered from the reflog for a while, but that is a safety net, not a backup.

Use it for abandoned experiments or branches you have verified are obsolete. It still cannot delete the checked-out branch, and it does not touch the remote.

Flags & arguments

-D
Force delete. Bypasses the merged check and is equivalent to git branch --delete --force.
feature/experiment
The branch to remove. Must not be the current branch. The slash is part of a valid branch name; spaces are never allowed.
!
Unmerged work can disappear.

Run git log --oneline main..feature/experiment first to see what only that branch contains. If any commit matters, merge or cherry-pick it before deleting. The remote branch, if any, must be deleted separately.

The golden rule

Inspect first. Delete second.

Git is designed to let you undo mistakes, but that protection ends where uncommitted work and shell deletions begin. Read the state, preview the action, then run the command.
